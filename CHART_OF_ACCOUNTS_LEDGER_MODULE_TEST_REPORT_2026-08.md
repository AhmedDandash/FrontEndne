## Headline: full CRUD auth bypass on the account tree — the referential backbone of the entire accounting system

**Create, Update (rename), Reporting-settings update, and Delete on `/api/V1/account/*` are all unauthenticated.** Each isolated-confirmed independently (fresh record, no-token write, follow-up authenticated `GET` to verify):

- **CREATE**: no-token request with a valid `X-Branch-Id` returned `200` with a real success message; confirmed persisted via a follow-up `settings` search.
- **UPDATE (rename)**: on a fresh, isolated leaf account, a no-token `PUT` returned `200`; a follow-up `GET` confirmed the submitted name was genuinely saved.
- **REPORTING (income-statement/P&L side + trial-balance grouping)**: on a fresh, isolated leaf account, a no-token `PUT` returned `200`; a follow-up `GET` confirmed the submitted values were genuinely saved.
- **DELETE**: on a fresh, isolated leaf account, a no-token `DELETE` returned `200`; a follow-up `GET` confirmed it was genuinely gone.

This is the same systemic no-auth pattern found in Modules #1–6 and #8, applied here to the account tree itself — every financial document in the system (journal entries, all 5 voucher types, every contract's accounting) ultimately posts against these accounts. An anonymous caller can rename any account, silently flip its income-statement/P&L classification, spray junk accounts into the tree, or delete any leaf account with no financial history — no token required for any of it.

## 🟠 MEDIUM — new backend bug: creating a root account with a leading digit outside 1–6 crashes (500)

Isolated with a direct discriminating test: `POST create-account` with a **root** (no `parentId`) code of `7`, `0`, or `99` each crashed with an empty-body `500`. The same call with code `10` (leading digit `1`, a known type — Asset) succeeded (`200`). **[round 2, strengthened]** Since `99` (2-digit, invalid leading digit) crashed while `10` (2-digit, valid leading digit) succeeded, code length was already ruled out as the confound in round 1, though the report didn't say so explicitly at the time. The Opus audit independently re-ran the discriminator to be sure: `"70"` → 500, `"80"` → 500, `"777"` → 500, while `"6"` (single digit, valid, previously-unclaimed type) → 200, `"15"` → 200. Leading digit is conclusively the variable, ruled out both ways. The account-type resolver appears to assume the leading digit is always one of the six documented types (1=Asset…6=AdminEx) and throws an unhandled exception instead of a clean `400` when it isn't. Low real-world likelihood through the actual UI (the create-account modal doesn't restrict the code's leading digit either, so a user typing a root code like "7" or "9" would hit this directly), but a genuine robustness gap — should be a validation error, not a crash.

## 🟡 MEDIUM — reporting-side enum values aren't validated server-side

`PUT /account/reporting/{id}` accepted `incomeStatementSide: 999` / `profitLossSide: 999` (the documented enum is 1=Debit, 2=Credit, 3=Hidden) with a `200` success response, and the value genuinely persisted — confirmed via a follow-up `GET` showing `incomeStatementSide: 999` stored verbatim. The frontend's `getReportSideLabel()` helper is defensively tolerant (falls back to rendering the raw number), so this doesn't crash the UI, but it lets garbage values into real financial classification data with no server-side guard rail.

## 🟡 MEDIUM — VAT report crashes (500) on a missing required `year` param

`GET /Ledger/vat-report?quarter=3` (no `year`) crashes with an empty-body `500`. By contrast, an out-of-range but *present* value (`quarter=5`) is correctly rejected with a clean `400`. Minor robustness gap — a missing required parameter should validate cleanly, not crash. Backend-only, cannot be fixed from this repo.

## What's working correctly (verified, not just assumed)

- **Business-rule guards on account deletion, both confirmed live**: deleting a non-leaf account (has children) is correctly blocked (`400`); deleting a leaf with real financial movements (Cash, which has posted ledger lines) is also correctly blocked (`400`).
- **Create validation, all backend-enforced**: duplicate account codes rejected (`400`), a child code that doesn't start with its parent's code rejected (`400`), a non-existent `parentId` rejected (`400`), missing `code`/`name` rejected (`400`).
- **The "returns only Posted data" claim, verified true**: a known Draft (unposted) journal entry's Cash movement does **not** appear in `general-ledger` for that account, even across a multi-year date range — confirmed by searching the ledger's line items for that entry's specific `entryNumber` and finding it absent.
- **Trial balance and balance sheet are mathematically sound**: `trial-balance` shows `totalDebit === totalCredit` exactly (both narrow and multi-year wide ranges tested); `balance-sheet` satisfies the accounting equation (`Assets = Liabilities + Equity`) to the cent (`58285.48 = 7449.93 + 50835.55`). **[round 2, softened]** This is a good consistency signal, but it's weaker than "strong evidence the whole system is internally consistent" as originally claimed: both checks compare server-provided aggregate totals against each other, not against an independent re-summation of the underlying line items — a bug in how those totals are aggregated server-side (as opposed to a bug in the double-entry logic itself) would still pass this check. Treat it as "the reports agree with each other," not as full proof of ledger correctness.
- **`customer-ledger` works correctly when there's real data — [round 2, now with saved evidence]**: the first customer tested returned `400 "No entries found"`, which looked suspicious until cross-checked — that specific customer genuinely has zero *Posted* journal entries (only Draft residue from earlier module testing). A different customer with real posted contract activity returned a correct, fully-populated ledger — 8 lines, confirmed via a saved log (round 1 asserted this but never actually saved the evidence; corrected in `coa-test4-audit-followup-results.json`). Not a bug; the 400 is the documented, correct behavior for a party with no posted history (already noted in the hook's own code comment).
- **`agent-ledger`/`worker-ledger` — [round 2, correction]**: round 1's endpoint table claimed these were verified with "real data," which was false — every logged call for both endpoints returned `400 "No entries found"`, and no success case was ever captured. Re-tested properly: swept **all 1 agent and all 14 workers** in the system against a 2015-to-now date range — **zero** have any posted ledger activity at all. So the 400 responses are correct given the current dataset, but the *success* response shape for these two endpoints remains genuinely unverified — there is currently no party in this system with posted activity to demonstrate it against. Flagged honestly rather than left as an unstated gap.
- **Inverted date ranges (`from` after `to`) are handled gracefully** — `general-ledger` returns a valid empty-movement response (opening balance shown, zero debit/credit, empty lines), not a crash or nonsensical data.
- **A future period with genuinely no data** (`vat-report?year=2099&quarter=1`) returns a clean, well-formed zero-valued response — no crash.
- All GET endpoints (tree reads, settings, all 8 ledger reports) are anonymous-accessible — consistent with the GET-endpoints-generally-unauthenticated pattern seen across the whole app, not specific to this module.
- `Accounts-list` (`GET /api/V1/Account/Accounts-list`) exists on the backend but isn't wired into `api.config.ts` or used anywhere in the frontend — it returns a flat (non-hierarchical) subset of account nodes. Functionally redundant with `full-tree-structure` + `subtree`, which the app already uses; noted as an unused endpoint, not a gap that needs closing.

## 🟡 MEDIUM — 4 UI action handlers had unhandled mutation rejections (frontend, fixed)

Same bug class fixed in several prior modules this session, found across two files sharing the module's mutation hook:

- `src/app/accounting/_components/AccountModals.tsx` — `submitCreate`/`submitName`/`submitReporting` each `await` their respective `mutateAsync` call with no try/catch, inside a plain antd `<Modal onOk={...}>`. Confirmed directly against the antd source in this repo (`node_modules/antd/lib/modal/Modal.js`): `handleOk = e => { onOk?.(e); onClose?.(); }` — no await, no catch.
- `src/app/accounting/chart-of-accounts/page.tsx` — `confirmDelete`'s `Modal.confirm({ onOk: () => deleteAccount(node.id) })`. **A correction to working knowledge established earlier this session**: `Modal.confirm()` was previously assumed safe (unlike the plain `<Modal>` component) because it doesn't prematurely close on failure — that part is true, verified again here. But tracing the actual mechanism (`ConfirmOkBtn.js` → `ActionButton.js`'s `handlePromiseOnOk`) shows that on rejection it still does `return Promise.reject(e)` from inside the `.then()` failure handler, as an orphaned promise nothing ever consumes — unless `isSilent()` returns true, which the static `Modal.confirm()` API never sets. So `Modal.confirm()`'s "safety" only covers *not closing prematurely*, not the unhandled-rejection class of bug; this call site had the same defect as the plain-`Modal` ones.
- `src/app/accounting/account-settings/page.tsx` — a `Popconfirm.onConfirm={() => deleteAccount(record.id)}` firing the bare `mutateAsync` with no `.catch()`.

**Fixed**: all 4 wrapped/chained appropriately (try/catch for the two `Modal`/`Modal.confirm` handlers, `.catch(() => {})` for the `Popconfirm` handler) — consistent with the pattern used throughout this session.

**[round 2, three follow-ups from the audit]**

1. **`validateFields()` was left outside the try in all three `AccountModals.tsx` handlers.** Since antd's `handleOk` discards whatever `onOk` returns without awaiting, a *form-validation* rejection (the more common failure mode — an invalid field, not a mutation error) was still unhandled after the round-1 fix. Corrected: the try block now wraps `validateFields()` too. This is safe — antd's Form component shows its own inline field-error UI independently of whether the caller catches the rejection, so nothing about the visible validation UX changes; only the unhandled-rejection warning goes away.
2. **A pre-existing, unrelated bug surfaced in passing**: `useAccounts.ts`'s four `onError` handlers read `err.response?.data?.message`, but this backend's error envelope is `{ success:false, errors:[...], statusCode }` — there is no `message` field, so every account-mutation failure showed only the generic bilingual fallback text, never the server's actual reason (e.g. "cannot delete an account with sub-accounts"). Fixed by switching all four to the shared `getApiErrorMessage()` helper (`src/utils/api-error.ts`), already used correctly elsewhere in the app for this exact envelope shape.
3. **An honest trade-off in the `Modal.confirm()` fix, disclosed rather than silently accepted**: catching the rejection inside `confirmDelete`'s `onOk` means the handler's returned promise now always *resolves* — which means antd's `ActionButton` always takes its success branch and closes the confirm dialog, even when the delete actually failed (previously, the unhandled-rejection version left the dialog open on failure, as an accidental side effect of never resolving). The `onError` toast still fires and explains the failure either way, so no error is silently swallowed — but the dialog no longer stays open for an immediate retry. This makes `Modal.confirm()`'s behavior on failure consistent with how the sibling `Popconfirm`-based deletes already behave elsewhere in this app (their popover closes immediately regardless of outcome too), so it's a defensible trade rather than a regression, but it is a real, deliberate behavior change worth the user knowing about rather than presenting as a pure bug fix.
