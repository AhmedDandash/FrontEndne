## A note on testing approach for this module specifically

This is the smallest module tested so far (4 endpoints) but arguably the highest-blast-radius one: the current year (2026) is where every module tested this session — and all remaining ones — creates its test data, and closing it would block posting company-wide for the rest of this audit. Rather than test the close/open mutations directly against 2025 (already closed, with substantial real closing history) or 2026 (the live year), the live backend was probed first for whether it accepts a synthetic, out-of-range year with zero real transactions — it does (see below) — and that synthetic year (2030) was used to fully exercise the close→verify→reopen→verify cycle instead. This validated the mechanism completely without ever touching 2025 or 2026's real state, which was independently re-confirmed unchanged at the end of testing.

## Headline: this is the first module in eleven where BOTH reads and writes correctly require authentication

**`GET /PeriodClosing` and `GET /PeriodClosing/status` return `401` for an anonymous request** — the first time any module's list/read endpoint has required authentication in this entire audit (Modules #1–10 were anonymous-readable across the board). **`POST /close` and `POST /open` also correctly return `401` with no token** (not a validation-layer `400` reached-without-auth pattern like the auth gaps found in prior modules — a genuine `401`, with a real ASP.NET `WWW-Authenticate: Bearer` challenge header). **[round 2, corrected]** The original claim that this was "confirmed both with a valid and with a deliberately-invalid body" for `/close` was overstated — both of this report's own no-auth `/close` attempts actually used the same out-of-range body (`year: 1900`); only `/open` was tried with a realistic body. The audit closed this gap directly: an anonymous `POST /close` with a valid, in-range body (`{"year": 2031}`) also returned `401`, with no mutation created. The audit also ran a same-session control (`GET /api/V1/Branch` anonymously → `200`) to rule out a proxy/network artifact — the 401s are specific to this controller, not a fluke of the test environment. This module appears to be properly secured end-to-end. Whatever configuration this controller uses is a second, independent example (after Employment Operating Contracts in Module #7) of the fix that should be applied everywhere else in the backend.

## 🟡 LOW — closing swept up nominal-account balances that weren't actually dated within the target year (backend, cannot be fixed from this repo — but genuinely reversible, verified)

Closing year `2030` — a year with no transactions of its own — returned a real, non-zero `netIncomeTransferred: 1755.39`. **[round 2, corrected mechanism]** The original framing described this as "cumulative net income" being transferred regardless of target year, which the audit's own live data check showed is not quite right and overstates the bug: the Operating Revenue account (404) currently holds exactly `1755.39`, composed of two real journal entries — one dated `2026-06-30` and one dated `2026-08-11` (the latter created by this very session's own Module #7 testing). What the backend actually does is close out **whatever balances currently sit in the nominal (Revenue/Expense) accounts at the moment `close` is called**, using the supplied `year` only as the closing entry's date/label — not as a filter on which transactions belong to that year. Expense accounts were already fully closed by an earlier period-close, which is why this particular closing entry only had a revenue leg. So the defect is narrower than "cumulative net income, wrong year": nominal balances aren't scoped to end-of-target-year, and closing a year with no activity of its own isn't rejected — it just sweeps whatever hasn't been closed yet, dated under whichever year happens to be passed in.

**This was fully and precisely reversed, independently verified with numbers, not just a status flag** — and independently re-verified a second time by the audit against the then-current live state, not just against this report's own numbers: the Retained Earnings account (302) balance was `31335.55` immediately after the close, and `29580.16` immediately after reopening — a difference of exactly `1755.39`, matching the transferred amount to the cent (audit's own re-check: current balance is still `29580.16`, composed of exactly the two pre-existing lines, with the 2030 line gone). A follow-up `GET` confirmed 2025 and 2026 were both completely unaffected throughout — 2025 retained its exact original `closedAt`/`closedBy`/`closingJournalEntryId`, and 2026 remained open. **[round 2, correction]** The original report also claimed "the year itself vanished from the `GET /PeriodClosing` list entirely once reopened (the endpoint only returns years with real closing history)" — this was never actually verified (the list was only checked *after* reopening, not while 2030 was still closed) and the audit showed the explanation is wrong: the list endpoint is simply range-bounded to `2025 → current year`, so a synthetic year like 2030 would never appear in it regardless of open/closed state. That claim is struck rather than repeated. The auto-generated closing journal entry reverted to `Draft` status on reopen (consistent with the existing Posting/Unposting reversal pattern) and was cleanly deleted as part of this session's cleanup — unlike the DELETE-crash bug found on source-linked journal entries in Module #8, this one deleted without issue, likely because its `referenceType` differs from the Contract/Payment/Adjustment sources that trigger that bug.

**Real-world impact**: low in practice — closing generally happens once per real year, in order, so unclosed nominal balances landing under the "wrong" year mostly matters for out-of-order or synthetic closes like this test exercised. Still worth a backend fix to date-scope the close to the target year's own activity and/or reject closing a year with no transactions dated within it.

## 🟡 MEDIUM — reopening a year leaves its closing journal entry stranded as an orphaned Draft, and this predates this session's testing (backend, cannot be fixed from this repo)

**[round 2, new finding, missed in round 1]** The audit found that treating the leftover Draft closing JE from the 2030 test as ordinary test-data cleanup undersold it — this is backend behavior, not test residue: reopening a year reverses the closing entry to Draft but never deletes or otherwise resolves it, and the audit found live proof this isn't new. Two other Draft closing journal entries already existed on the system before this session's testing began: `JE-2026-0042` ("إغلاق السنة المالية 2099") and `JE-2026-0045` ("إغلاق السنة المالية 2026") — both still sitting as `status: 0` (Draft), evidence of prior close/reopen cycles (likely from the module's original 2026-07 development/verification pass) whose closing entries were never cleaned up. Every reopen leaves one more of these behind indefinitely. Not a data-integrity risk (Draft entries have no ledger effect), but a real, accumulating housekeeping gap worth a backend fix — ideally reopening should delete the now-meaningless closing entry rather than leave it orphaned.

## What's working correctly (verified, not just assumed)

- **Authentication is correctly enforced on all four endpoints** — see headline.
- **Business-rule validation, mostly clean and correctly worded**: closing a year before 2025 rejected (`"لا يمكن إدارة سنة مالية قبل 2025"`); double-closing an already-closed year rejected (`"السنة المالية مغلقة بالفعل"` — "the fiscal year is already closed"), verified with zero state change; opening a year that isn't closed rejected (`"السنة المالية غير مغلقة"` — "the fiscal year is not closed"), verified with zero state change; a non-numeric `year` in the request body produces a clean ASP.NET model-binding `400`, not a crash. **[round 2, correction]** "All clean" overstated this: `GET /status` with no `year` param returns `200 {data: false}` rather than a `400` (a missing required query param silently reads as "not closed" instead of being rejected), and `POST /close` with no `year` in the body returns the *misleading* `"لا يمكن إدارة سنة مالية قبل 2025"` message — technically triggered because an absent year is bound as `0`, which is indeed before 2025, but the message doesn't reflect what actually went wrong (a missing field, not a genuinely out-of-range year).
- **The close→open cycle is genuinely, numerically reversible** — see the finding above. This is the strongest verification of financial-reversal correctness performed on any mutation this session (an exact-to-the-cent before/after ledger comparison, independently re-verified a second time by the audit against live state, not just a status-flag check).
- **The reopen correctly reverses the linked journal entry's Posted status back to Draft**, matching the existing Posting/Unposting reversal semantics rather than introducing new behavior (though see the new MEDIUM finding above — it's never cleaned up after that).
- **[round 2, correction]** The list-endpoint year-range documentation was previously called a "stale comment" needing a fix — this was backwards. `period-closing.service.ts`'s comment describing the range as "2025 → current year" is accurate *for the list endpoint specifically* (confirmed: 2030 never appeared in `GET /PeriodClosing` at any point, open or closed) — it's the `close`/`open` *mutation* endpoints that accept years beyond that range, which is a different, narrower observation than "the comment is stale." No code or comment change needed after all.

## 🟡 MEDIUM — `handleClose`/`handleOpen` had no catch, only a `finally` (frontend, fixed)

Same bug class fixed in nearly every module this session, in a slightly different shape: `src/app/accounting/period-closing/page.tsx`'s `handleClose` and `handleOpen` both wrapped their mutation call in `try { ... } finally { setBusyYear(null); }` — the `finally` correctly always clears the busy-spinner state, but with no `catch`, a rejected mutation (e.g., the double-close/already-open rejections exercised above, or a network error) still produced an unhandled promise rejection, since these handlers are called directly from `Popconfirm.onConfirm` with nothing else consuming the rejection. **Fixed**: added a `catch` block between the `try` and `finally` that swallows the rejection (the mutation's own `onError` already shows a toast). Repo-wide search confirmed `page.tsx` is the only consumer of `useClosePeriod`/`useOpenPeriod`.
