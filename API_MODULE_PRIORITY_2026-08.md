# API Module Testing Priority — Sigma Frontend (2026-08)

**Phase 2 deliverable — architecture analysis + prioritization. No code changes, no live testing performed.**

**Input:** `API_MODULE_INVENTORY_2026-08.md` (Phase 1 discovery, 43 module sections / ~186 claimed endpoints).

**Ranking method.** Every module was scored on nine weighted axes rather than raw endpoint count: (1) core-system dependency, (2) number of dependent modules, (3) auth/authorization impact, (4) business importance to the recruitment-agency revenue model, (5) financial / data-integrity risk, (6) endpoint count and workflow complexity, (7) breadth of frontend usage, (8) shared-service status (lookups, headers, party master data reused everywhere), (9) known-defect history and blast radius if broken. Where axes conflicted, **blast radius beat endpoint count** — a 6-endpoint module that gates every write in the app outranks a 32-endpoint module that only serves one page. Within a tier, order is also a workable **execution order**: dependencies are tested before their dependents so fixtures exist when you reach the consumer.

**Grouping.** Rows follow the inventory's own module sections, with two deliberate splits where the inventory's summary table was itself more granular than its section headings:
- Module 29 → split into **Period Closing** (🔴, gates all posting) and **Restriction Types** (🟡, a JE classification lookup with a known 501). Bundling a books-locking control with a lookup table would have mispriced both.
- Module 38 → split into the **Orders/Drivers/Catalog/Payments/Notifications** transaction family (🟠, contains refunds and invoice creation) and **Hourly Reports** (🟡, read-only).

That yields **45 rows covering all 43 inventory modules**, each appearing exactly once, in strict priority order.

## Top-5 Reasoning

The top five are ranked by **blast radius, not size**. **Authentication (1)** and **Branch Management (2)** are the two modules every other row in this table sits on top of: auth owns the token lifecycle and identity claims that gate all 140 pages, and Branch owns the `X-Branch-Id` GUID that the backend requires on *every* write in the system plus the BranchGate that blocks the UI until it resolves. Because the prior audit showed the backend validates that header far more reliably than it validates the JWT, branch context is effectively the real authorization boundary — a wrong branch id doesn't error, it silently writes correct-looking data into the wrong tenant, which is the worst failure mode in the inventory. **Customers (3)** and **Workers (4)** follow as the two party entities that nearly every downstream module joins against: between them they are referenced by both contract families, transfer contracts, complaints, housing, medical exams, all five accounting document types, and three of the ledger reports, so a shape or id defect here propagates into contracts and books before anyone notices. Workers additionally carries a known list-vs-detail field divergence. **Worker Master & Status Log (5)** is deliberately pulled up to sit beside Workers despite being an unglamorous set of twelve lifecycle mutations, because it is almost entirely write-only with no read-back surface — precisely the shape in which the known "silent no-op create" and "DELETE returns 200 for non-existent GUID" backend defects hide — and because those states (housed, deported, handed over, residency issued, wants-work/wants-transfer) are what determine whether a worker is even eligible for the revenue workflows ranked immediately below at 6 and 7.
