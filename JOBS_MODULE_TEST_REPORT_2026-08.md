# Jobs Module — Phase 3 Test Report

**Priority #12 — 🟠 High.** Tested 2026-08-12 against the live backend `https://sigma-api.runasp.net`. Raw logs (scratchpad): `jobs-test1.mjs`/`-results.json` (reads, create validation), `jobs-test2.mjs`/`-results.json` (isolated update/delete auth checks, cleanup), `jobs-test3-round2.mjs`/`-results.json` (round-2 follow-up after an Opus audit pass — see "Round-2 audit summary" below).

> **Round-2 corrections (post Opus audit, verdict: needs-rework, narrow):** the audit found this report's own raw log already contained direct evidence of a more severe bug than anything actually written up — a silent list-truncation issue in the one code path this module's frontend genuinely exercises — and that it went unnoticed. It also corrected an undercounted consumer list, an overstated "real usage" claim, and a cleanup verification that was weaker than described. All four are corrected below, marked **[round 2]**, along with a properly-attempted (if inconclusive) test of the delete-blocked-if-referenced business rule that round 1 had skipped outright.

## Scope note: this module is almost entirely dead code in the frontend

Before testing, code inspection found that of this module's 5 backend endpoints, only **one** — `GET /api/V1/Job` via `JobService.getAll()` / `useJobs()` — has any live consumer anywhere in the app. `getPaged()`, `getById()`/`useJob(id)`, and all three write hooks (`useCreateJob`, `useUpdateJob`, `useDeleteJob`) are fully implemented — service methods, typed DTOs, React Query hooks, error handling, success toasts — but **wired into zero pages**. There is currently no UI anywhere in this app to create, edit, or delete a job. All 5 endpoints were still tested directly against the API per the standard Phase 3 process, but the practical impact of anything found below should be read through that lens: only the read path is something a real user's session actually exercises today. **[round 2, correction]** The original count of "6 dropdown-population sites" was wrong — a full repo-wide search (independently re-run by the audit) found **13 files** actually consuming `useJobs()`: `applicants/page.tsx`, `customers/page.tsx`, `components/contracts/RentOfferSelector.tsx`, the 4 `rent-prices-offers` pages, the 3 `mediationcontract` pages, both `operation/rent` pages, and `settings/mediation/page.tsx`. The "only `getAll()` is live" conclusion itself was correct and re-verified; only the consumer count understated its own reach by more than 2×.

## 🔴 HIGH — `JobService.getAll()` silently truncated the job list at 10, in the one code path this module's frontend actually uses (frontend, fixed)

**[round 2, new finding — missed in round 1 despite the evidence sitting in its own raw log]** `getAll()` called `GET /api/V1/Job` with no query parameters at all. The backend defaults to a page size of `10` when none is supplied — live-verified this session: with 14 real jobs on the system, the unparameterized call returned exactly `10`, silently dropping the other 4 (including two real, non-QA master-data jobs — "Private Driver" and "Housemaid" — cut off by nothing more than list order). `jobs-test2-results.json` from round 1 already showed `totalCount: 11, pageSize: 10, items: 10` in its own output and this was never flagged.

Since `getAll()`/`useJobs()` is confirmed the *only* live-exercised path in this entire module (see above — 13 real consumers), this is a genuine, currently-live data-loss-in-UI bug: any job dropdown across the app (worker creation, mediation/operating offer forms, customer contract creation, the settings pages) silently loses entries once the system has more than 10 jobs configured, with no error, no indication, nothing — the 11th+ job simply cannot be selected anywhere. This is more severe in practice than the error-swallowing bug documented below, which only matters during an actual backend failure; this one is live under completely normal, successful operation.

**Fixed**: `getAll()` now sends `PageSize: 9999`, matching the pattern already used by other services in this codebase for "give me the whole unpaged list" (e.g. `EmploymentOperatingContractService.getAll()`). Re-verified live: reproduced the exact truncation with a fresh 14-job system (10 returned with no params), then confirmed the fixed call returns all 14. Test jobs cleaned up; the two real master-data jobs that had been silently hidden were unaffected throughout (never touched, only their absence from the truncated list was observed).

## 🟠 HIGH — full CRUD auth bypass on Jobs (backend, cannot be fixed from this repo)

**Create, Update, and Delete are all unauthenticated**, each isolated-confirmed independently (fresh record, no-token write, follow-up authenticated read to verify):

- **CREATE**: a no-token request with a valid `X-Branch-Id` header returned `200` with a real success message (`"تم إضافة الوظيفة بنجاح"`); confirmed persisted via a follow-up authenticated `GET`.
- **UPDATE**: on a fresh, isolated job, a no-token `PUT` returned `200`; a follow-up `GET` confirmed the submitted name change was genuinely saved.
- **DELETE**: on a fresh, isolated job, a no-token `DELETE` returned `200`; a follow-up `GET` returned `404`, confirming it was genuinely gone.

Same systemic pattern found in nearly every module this session. Given the current lack of any frontend CRUD surface for this module (see above), the practical exposure today is that this master-data table can be freely tampered with by anyone who can reach the API directly — not through this app's own UI, since none exists.

**[round 2, correction]** Round 1 deferred testing whether `DELETE` is blocked when a job is actively referenced by other records ("delete-blocked-if-referenced") — it targeted a real, named job ("Private Driver") but then skipped the actual delete entirely to avoid risking real master data, leaving the business rule completely unverified. The audit correctly called this an avoidable gap: a fully disposable version of the same test was available (create a throwaway job, reference it from a throwaway record, then attempt delete) and should have been used instead of skipping. Attempted properly this round: created a disposable job, then attempted to create a Mediation Contract Offer referencing it (the cheapest real "something points at this job" record in the system) to establish a genuine reference before testing delete. That setup step itself crashed with an empty-body `500` — a `MediationContractOffer`-side issue unrelated to Jobs, out of scope for this report. Since no genuine reference was ever established, the subsequent delete succeeding proves nothing about the business rule either way. **This remains genuinely untested** — an honest "attempted, blocked by an unrelated bug" is reported here rather than either repeating the outright skip or asserting a false conclusion from a delete that had nothing real to guard against.

## 🟡 MEDIUM — a job can be created with no name at all (backend, cannot be fixed from this repo)

`POST /api/V1/Job` with an empty body, or with both `jobNameAr` and `jobNameEn` explicitly omitted, succeeds (`200`) and creates a real, permanent, completely nameless job record. This isn't a hypothetical edge case: the live system already had **one pre-existing nameless job** (`a00a3007-cd97-4f00-9b6b-08dedd448ae3`, both name fields `null`) before this session's testing began. Two more were created and confirmed during this pass, then cleaned up. **[round 2, correction]** The original framing claimed this "has already happened in real usage" — but per this module's own scope note, there is no frontend UI capable of creating a job at all, so that pre-existing record cannot have come from a real user; it must have come from a direct API call (a seed script, backend tooling, or prior ad-hoc/test activity). Its GUID sequence places it after the original seed batch and before this session's own test records, consistent with prior test activity rather than end-user traffic. The validation gap itself is exactly as real either way — a real, permanent, nameless record can be created with no error — but the finding is corrected to not overclaim what kind of "usage" produced the one already on file.

Every dropdown across the app that lists jobs (`settings/mediation/page.tsx` and the other 12 consumers) falls back to rendering the raw GUID as the label when both name fields are empty (`j.jobNameAr || j.jobNameEn || String(j.id)`), so this doesn't crash the UI — but it does mean a real user could end up selecting an unlabeled, GUID-named entry from a job picker with no indication of what it actually represents. Backend validation should require at least one of the two name fields to be non-empty.

## What's working correctly (verified, not just assumed)

- **`GET /Job/{id}`** returns `404` for a non-existent id and `400` for a malformed one — standard, correct behavior.
- **List filters/pagination params are accepted without error** (`PageNumber`/`PageSize`/`SearchName`), though — per the scope note above — no frontend page actually drives these; `getPaged()` is dead code.
- GET endpoints (list, by-id) are anonymous-accessible — consistent with the GET-endpoints-generally-unauthenticated pattern seen across the whole app, not specific to this module.

## 🟡 MEDIUM — `JobService.getAll()` silently swallowed every failure into an empty array, masking real backend errors as "no jobs available" across every live consumer (frontend, fixed)

Unlike the auth/validation findings above, this is a *live*, currently-reachable bug — `getAll()` is the one code path this module's frontend actually exercises. The method wrapped its entire body in a `try/catch` that, on **any** failure — a genuine `500`, a network error, an auth problem, anything — logged to the console and returned `[]`. Since `useJobs()` is a plain `useQuery` with no error handling of its own, this meant a real backend outage would never surface as an error state anywhere: every one of the 13 job-dropdown consumers (see the corrected count above) would simply render an empty, silently-degraded dropdown with no indication anything was wrong — indistinguishable from "there genuinely are no jobs configured." This is the same class of silent-failure risk flagged repeatedly elsewhere this session, just via a `try/catch` instead of a missing `await`/`catch` on a mutation.

**Fixed**: removed the `try/catch` so a genuine failure now propagates normally to React Query's error state, exactly like every sibling service in this codebase (`getPaged()`, in the very same file, was already written this way). The defensive response-shape-detection logic (trying several possible envelope shapes) was kept as-is, byte-identical — that's legitimate parsing tolerance, not the bug. **[round 2, correction]** The round-1 write-up said "two leftover debug console statements" were removed — there were actually three (two `console.log`, one `console.error`) tied to `getAll()` itself, plus two more unrelated debug `console.log` calls in `create()` and `update()` that round 1 left in place. All five are now removed, consistent with the same housekeeping already applied to this file for the same underlying reason (debug logging that shouldn't ship).

`JobService.getById()` has the identical swallow-to-`null` pattern, but — per the scope note above — its only consumer (`useJob(id)`) has zero call sites anywhere in the app, so it was left unchanged rather than fixing dead code; noted here for completeness in case a future feature wires it up.

## Cleanup

**[round 2, correction]** Round 1 claimed all test jobs were "deleted and verified gone via a final list sweep" — the verification method was weaker than described: the sweep queried the list with no `PageSize` (the same unparameterized call the HIGH finding above proves truncates at 10), and with `totalCount: 11` at the time, one real job ("Housemaid") was sitting on a second page that was never actually inspected. It happened to work out — newest-first ordering meant every QA-created record was still within the first 10 results — but the claim of "verified" wasn't backed by a query capable of seeing everything. Re-swept properly this round with `PageSize=9999` after all round-2 testing (including 8 additional seed jobs created specifically to reproduce the truncation bug): final residue from this session's own testing is genuinely **0**, now confirmed by a query that cannot itself miss anything. The one pre-existing nameless job (`a00a3007-...`, predates this session) was deliberately left untouched throughout — it isn't this session's residue, and deleting a real system record wasn't this audit's call to make.

## Round-2 audit summary

The Opus audit returned **needs-rework (narrow)** — its own framing, since the structural "dead code" claims held up but the module's one live code path had a more serious, missed bug sitting in the report's own evidence. It independently re-derived the consumer count (13, not 6) via its own repo-wide search, reproduced the truncation bug live with a fresh 14-job seed, and confirmed the fix resolves it. It also corrected the nameless-job "real usage" overclaim and the weak cleanup verification, and pushed back on round 1's decision to skip the delete-blocked-if-referenced test entirely rather than use a safe, fully disposable version of the same probe. That test was attempted properly this round — it did not reach a conclusion (an unrelated endpoint crashed before a real reference could be established), but that is now stated honestly rather than left as a silent gap or asserted as a false negative. No further audit round requested; corrections applied directly.
